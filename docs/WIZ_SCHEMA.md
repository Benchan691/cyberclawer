# Wiz schema and implementation handoff

This document describes the Wiz integration implemented in Cyberclawer as of
2026-11-18. Use the stored MongoDB document contract below when building another
application that consumes this data.

## 1. Integration contract

| Setting | Implemented value |
| --- | --- |
| Provider key | `wiz` |
| Feed | [Cloud Threat Landscape RSS](https://www.wiz.io/api/feed/cloud-threat-landscape/rss.xml) |
| Source homepage | [Cloud Threat Landscape](https://threats.wiz.io/) |
| MongoDB collection | Shared `news` collection, or the configured shared collection name |
| Provider filter | `{ "source.provider": "wiz" }` |
| Document identity | `wiz:<RSS GUID>` |
| Code | Normalized, lowercase UUID string with hyphens |
| Permanent article URL | `https://threats.wiz.io/<GUID without hyphens>`; follows the redirect to the current article slug |
| Source entry types | `Campaign`, `Incident`, `Research`; retain other source values if encountered |
| Storage schema version | `2` |
| Fetch method | HTTP: RSS XML followed by server-rendered article HTML |
| Authentication | No Wiz-specific credentials or API key are configured |
| Default request delay | `1.0` second; shared request/concurrency settings remain configurable |

The GUID identifies an incident even if its title or article slug changes.
One feed item produces one news document. An item mentioning several CVEs stays
one document with a `cve_ids` array.

## 2. Stored MongoDB structure

The following is the normal successful Wiz document shape. `?` marks a field
that a consuming application must allow to be absent.

```text
news
├── _id: string                         "wiz:<guid>"
├── schema_version: integer             2
├── code: string                        "<guid>"
├── title: string
├── observed_at: BSON Date
├── published_at?: BSON Date
├── updated_at?: BSON Date
├── cve_ids?: string[]                   full "CVE-YYYY-NNNN..." identifiers
├── source: object
│   ├── provider: string                "wiz"
│   ├── url?: string                    "https://threats.wiz.io/"
│   └── detail_url?: string             permanent GUID URL
└── details: object
    ├── content: string                 plain text with newline-separated blocks
    ├── summary?: string
    ├── article_url?: string            canonical human-readable article URL
    ├── threat_type?: string
    ├── actors?: string[]
    ├── initial_access?: string[]
    ├── impact?: string[]
    ├── observed_techniques?: string[]
    ├── targeted_technologies?: string[]
    ├── source_status?: string
    ├── reference_links?: string[]
    └── author?: string
```

MongoDB stores the date fields as BSON dates. An API exposing these records can
serialize them as ISO 8601 UTC strings, such as `2026-11-18T03:00:00Z`.
That API serialization layer is a responsibility of the consuming project.

Empty strings, `null`, empty arrays, and empty objects are removed during storage
normalization. Consumers should default missing list fields to `[]` and display
missing scalar fields as unavailable.

### Top-level fields

| Field | Meaning and behavior |
| --- | --- |
| `_id` | Stable key for deduplication, updates, links, and UI item keys. Format: `wiz:<guid>`. |
| `schema_version` | Always `2` for this storage format. |
| `code` | The RSS GUID, parsed as a UUID and normalized to lowercase with hyphens. |
| `title` | RSS title with a trailing `(Campaign)`, `(Incident)`, or `(Research)` removed. |
| `observed_at` | Scraper observation time associated with the stored record. An unchanged record is skipped, so this is not a last-polled timestamp. |
| `published_at` | Article `Pub. date`, falling back to RSS `pubDate` if absent or unparseable. Omitted if neither supplies a valid date. |
| `updated_at` | Article `Last edited`. The shared timestamp layer falls back to the publication time if an edit date is unavailable. It does not always prove that an edit occurred. |
| `cve_ids` | Unique uppercase identifiers found in the article title, summary, content, or reference URLs, merged with those extracted from the RSS title and summary. Omitted when empty. |
| `source.provider` | Always `wiz`; use this field to select Wiz records from the shared collection. |
| `source.url` | Configured source homepage, normally `https://threats.wiz.io/`. |
| `source.detail_url` | Permanent GUID URL used for the detail request, rather than the potentially stale RSS slug URL. |

The current Wiz provider supplies no severity rating and no `new`/`updated`
source status. Consequently, normal Wiz documents omit top-level `severity` and
`change_type`. The shared schema reserves these optional fields, but they are
not generated by this integration. `classification` is reserved for the `cve`
provider and is not allowed on Wiz documents.

### Fields inside `details`

| Field | Type | Source and meaning |
| --- | --- | --- |
| `content` | `string` | Full available article text. Paragraph/block boundaries become newlines. Navigation, page-property controls, scripts, styles, footers, and SVG elements are excluded. For historical entries with no prose, content is composed from the page summary and nonempty structured properties. |
| `summary` | `string` | Page `<meta name="description">`, falling back to the RSS summary. |
| `article_url` | `string` | Page canonical URL, falling back to `og:url`, then to the RSS article link during finalization. Article URLs must be HTTPS links under `threats.wiz.io/all-incidents/`. |
| `threat_type` | `string` | Page `Type`, falling back to the recognized RSS title suffix. |
| `actors` | `string[]` | Labels in the page `Actors` property. |
| `initial_access` | `string[]` | Labels in `Initial access`. |
| `impact` | `string[]` | Labels in `Impact`. |
| `observed_techniques` | `string[]` | Labels in `Observed techniques`. These are source labels, not a normalized MITRE technique-ID contract. |
| `targeted_technologies` | `string[]` | Labels in `Targeted technologies`. These are source labels, not normalized vendor/product/CPE classifications. |
| `source_status` | `string` | Page `Status`, for example `Finalized`. This is the source's editorial status. |
| `reference_links` | `string[]` | Deduplicated permanent URL, article URL, and HTTP/HTTPS links from the article and its properties. Relative links are resolved to absolute URLs. Linked pages are not recursively fetched. |
| `author` | `string` | RSS `author`, falling back to namespaced `creator`. Preserved as the original string rather than split into name/email fields. |

`details` is an open object. If the article title differs from the RSS title,
`details.title` can remain alongside the top-level title. Consumers should tolerate
additional detail fields while using the fields above as the current contract.

### Normalization of intermediate fields

The provider first builds a detail object containing `feed_guid`, `title`,
`published_at`, `updated_at`, and `cve_ids`. The shared storage layer promotes or
deduplicates those values:

| Intermediate field | Stored location / normalization |
| --- | --- |
| `feed_guid` | `code`, with `wiz:` added for `_id`; the matching duplicate is removed from `details`. |
| `title` | Top-level `title`; an identical duplicate is removed from `details`. |
| `published_at` | Top-level BSON `published_at`; matching duplicate removed from `details`. |
| `updated_at` | Top-level BSON `updated_at`; matching duplicate removed from `details`. |
| `cve_ids` | Top-level `cve_ids`; matching duplicate removed from `details`. |
| `article_url` | Normally retained in `details` because the canonical slug URL differs from the permanent `source.detail_url`. Removed if it exactly duplicates a stored source URL. |
| `_list_summary` | Marks incomplete RSS metadata during processing. Successful article records do not carry it. Failed detail requests are not written as successful summary-only replacements. |

## 4. Implemented ingestion behavior

| Area | Implemented behavior |
| --- | --- |
| Provider registration | Package discovery registers `wiz`; `get_provider("wiz")` creates its provider. |
| RSS parsing | Namespace-aware XML parsing; prefers `content:encoded` over `description`, strips HTML from summaries, and parses publication dates. |
| Entry validation | Requires a valid UUID GUID, nonempty title, and valid Wiz incident link. Malformed entries are skipped; duplicate GUIDs are ignored. |
| Empty/error feeds | A valid channel with zero items is exhausted. Invalid XML, a missing channel, or a nonempty feed with no usable entries is an error. |
| Feed coverage | Reads all valid items exposed by the current feed; no hardcoded 50-item cap and no historical pagination. |
| Permanent URLs | Builds the detail URL from the GUID and follows redirects, allowing a renamed article to be fetched even if its RSS slug is obsolete. |
| Article extraction | Reads `article.notion-root` and `h1.notion-header__title`, extracts the page properties, prose, references, and CVEs. |
| Historical entries | Accepts verified article pages containing only structured metadata and preserves their available content. |
| Detail failures | Missing article/title/content or failed HTTP requests are failures. Existing full documents survive; shared catch-up retry state schedules recovery. |
| Date handling | Parses RSS dates, ISO dates, and the source's English dates. Normalizes to UTC; timezone-free source dates are interpreted as UTC by the Wiz parser. |
| Merge rules | Article detail takes precedence; missing identity/title/URL/type/publication/summary/author fields are supplemented from RSS. CVEs and references are deduplicated. |
| Shared storage | Writes to the configured shared collection with `source.provider = "wiz"` and schema-v2 normalization. |
| Catch-up discovery | `providers = ["all"]` automatically includes Wiz. An explicit provider list must contain `wiz` to include it. |
| Source catalog | Shared source-catalog publishing includes Wiz when enabled, allowing another application to offer a Wiz filter before the first article is stored. |
| Retry/backoff | Uses the existing HTTP retry/backoff, error logging, and configured failure-notification infrastructure. |

### Catch-up and updates

Wiz reads the full current feed and follows the shared date policy:

1. Poll the current feed and select entries up to the invocation's `--limit`.
2. Verify article publication/edit dates where RSS does not expose enough date
   information. Accept only articles published or updated within `--days`.
3. Insert missing records, replace changed records, and skip unchanged records.
4. Preserve eligible unfinished feed work and retries across invocations;
   identical snapshots resume within the current window. Expired work is retired.
5. Retain stored news records when they disappear from the feed.

`--limit` counts advisory/date checks, including unchanged or excluded records.
Both `run` and `catch-up` default to `--days 1`: published or edited today in
Hong Kong time. Old unchanged articles are not saved, even if still in RSS.
The feed has no article edit dates, so pages can require a date check before
they are excluded. Changing only the
scrape observation time does not cause an otherwise unchanged document to be
rewritten. BSON UTC representation and millisecond precision are accounted for
during content comparison.

Shared operational state lives in `news_sync_state` when the news collection is
`news`; local feed/work snapshots live under `data/sync-cache/wiz/`. These are
scraper progress records, separate from the news document schema.

## 5. Consuming Wiz from another project

Read the shared collection using the provider discriminator:

```javascript
db.news.find(
  { "source.provider": "wiz" },
  {
    _id: 1,
    code: 1,
    title: 1,
    published_at: 1,
    updated_at: 1,
    observed_at: 1,
    cve_ids: 1,
    source: 1,
    details: 1
  }
).sort({ observed_at: -1, _id: -1 }).limit(50)
```

| Consumer concern | Contract to use |
| --- | --- |
| Provider filtering | `source.provider === "wiz"`; the physical collection contains other providers too. |
| Body | `details.content`, rendered as plain text with paragraph/newline handling. |
| Canonical article link | `details.article_url` when available; fall back to `source.detail_url`. |
| Stable item key | `_id`. Keep `code` as the unprefixed GUID. |
| Lists/tags | Use the arrays in `details`, defaulting missing values to empty arrays. |
| CVE badges/search | Top-level `cve_ids`, defaulting to an empty array. |
| Dates | Serialize BSON dates explicitly at your API boundary. `published_at` is the source publication time; `observed_at` is the stored observation time. |
| Editorial status | `details.source_status`, separate from security severity or scraper success. |
| Missing severity | Display as unavailable if needed; do not derive a rating from the editorial status. |
| Provider selector | The shared `source_catalog` document with `_id = "active"` contains a `providers` string array. |

**Storage versus scraper output:** internal runner/export records have
`details.wiz`, `type = "wiz"`, `vuln_type`, `disclosure_date`, and bare
`cve_codes` such as `2026-12345`. MongoDB schema v2 flattens Wiz content to
`details`, identifies the source with `source.provider`, and stores full CVE IDs
at top level. The consumer contract in this document is the MongoDB format.

## 6. Implementation files

Paths below are relative to the Cyberclawer repository root.

```text
vuln_scraper/scrapers/wiz/
  config.py                   source URLs and legacy collection identifier
  provider.py                 discovery, GUID URL generation, schema mapping, merge rules
  parsers/
    common.py                 text, URL, CVE, and UTC-date helpers
    list.py                   RSS -> ListPage / ListEntry
    detail.py                 HTML -> WizDetailRecord

tests/scrapers/wiz/
  fixtures/
    list.xml                  representative RSS, duplicates, malformed entries
    detail.html               representative article and structured properties
  test_wiz_parsers.py          field extraction, validation, normalization
  test_wiz_provider.py         registration, limits, catch-up, updates, retries
```

Shared integration points are `vuln_scraper/sync_engine.py` (`wiz` in `FEEDS`),
the automatic scraper registry, `schema_v2.py`, `models.py`, `mongo.py`,
`source_catalog.py`, and `sync_state.py`.

Reusing the provider in a different application requires adapting its
`ListEntry`/`ListPage` interfaces and storage/sync dependencies, or consuming the
existing `news` collection directly. The parser package is not a standalone SDK.
It uses Python 3.11+, Beautiful Soup, and lxml; the existing runner uses httpx and
MongoDB integration uses pymongo. No new dependency was added for Wiz.

## 7. Commands and verification

Run Wiz with the existing configured MongoDB settings:

```bash
vuln-scrape run wiz --limit 20
```

Run the configured catch-up providers, including Wiz when enabled:

```bash
vuln-scrape catch-up --limit 1000 --days 1
```

Publish the source catalog without scraping:

```bash
vuln-scrape sync-source-catalog
```

Run the Wiz tests:

```bash
python -m pytest -q --import-mode=importlib tests/scrapers/wiz
```

## 8. Coverage limits and work for the consuming project

- Coverage is limited to entries currently exposed by the RSS feed. There is no
  separate historical archive crawl for entries absent from it.
- Source fields remain optional; a verified historical entry can contain
  structured metadata without prose. Unknown future source values should be
  tolerated by consumers.
- Dates without a timezone follow the Wiz parser's UTC interpretation. An
  absent edit date can yield an `updated_at` equal to the publication date.
- Feed `lastBuildDate` is not used as an incident's publication or edit date.
- The integration stores text and extracted fields. It does not retain raw HTML,
  download enclosures/images, or fetch every linked reference.
- It does not produce normalized CPE classifications, MITRE IDs, structured IoC
  collections, source severity ratings, or an article revision history.
- Cyberclawer provides ingestion and storage. API routes, UI pages, filtering
  controls, API date serialization, and authentication for the consuming
  application remain work for that project.
